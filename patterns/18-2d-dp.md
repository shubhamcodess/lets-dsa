# 2-D Dynamic Programming

_Pattern id: 18-2d-dp · Depends on: 17-1d-dp · Problems available: 11_

## The one-sentence idea
Extend the same overlapping-subproblems idea to two independent indices — usually a position in each of two sequences, or a position plus a remaining budget — and fill a grid of answers instead of a line.

## How to recognize it
- Two strings (or sequences) are being compared, transformed into one another, or matched against each other.
- The problem is set on a literal grid, and asks about paths, sums, or reachability across it.
- There's a budget, capacity, or count alongside a sequence — a knapsack-shaped constraint where you track both "how far into the items" and "how much capacity/budget is left."

## The invariant
dp[i][j] answers the subproblem restricted to the first i elements of one dimension and the first j elements (or units of budget) of the other — and depends only on cells with smaller i, smaller j, or both.

## The shape
1. Define the state: state precisely what dp[i][j] means in words — e.g., "the edit distance between the first i characters of word A and the first j characters of word B," or "the number of distinct ways to reach cell (i, j)." Getting this sentence exactly right is what makes the rest solvable.
2. Write the recurrence: express dp[i][j] in terms of a small number of neighboring cells — typically dp[i-1][j], dp[i][j-1], and dp[i-1][j-1] — matching how the problem lets a smaller pair of prefixes extend into a bigger one (match/mismatch, take/skip, move right/move down).
3. Identify base cases: the first row and first column, where one of the two dimensions is at its boundary (0 elements of one sequence, or the edge of the grid), and must be set directly from the problem's definition rather than derived from the recurrence.
4. Choose the iteration order: fill row by row (or column by column) so that whenever dp[i][j] is computed, every cell it depends on — always strictly earlier in at least one dimension — is already filled. The order matters because computing a cell before its dependency exists silently uses a stale or default value instead of the real one.
5. Read the final answer from a specific cell (often the bottom-right corner, dp[n][m]) once the whole grid is filled.

## The named algorithms
| Algorithm | What it computes | Key idea | Cost |
|---|---|---|---|
| Longest Common Subsequence (LCS) | The longest sequence of characters appearing in the same relative order in both of two strings | If the current characters of both strings match, extend the best answer from one index back in both; if they don't match, take the better of dropping one character from either string | O(n·m) time, O(n·m) space (O(min(n,m)) if rolled to two rows) |
| Edit distance (Levenshtein) | The minimum number of single-character insertions, deletions, and substitutions to turn one string into another | Same match/mismatch structure as LCS, but a mismatch allows three possible operations (insert, delete, substitute), each mapping to a different neighboring cell | O(n·m) time, O(n·m) space |
| Knapsack (0/1 and unbounded) | The best value achievable from a set of items under a weight/capacity budget | The state tracks both which items have been considered and how much capacity remains; each item is either taken (reducing capacity, adding value) or skipped | O(n·capacity) time, O(n·capacity) space (often rolled to O(capacity)) |

These three formulations cover almost every 2-D DP problem: LCS and edit distance are the "two sequences" shape, and knapsack is the "one sequence plus a budget" shape described in the core idea.

## Worked micro-example
Take the edit-distance idea on two tiny strings: "ab" and "b". dp[i][j] = edit distance between the first i characters of "ab" and the first j characters of "b".
Base cases: dp[0][j] = j (turn empty string into first j chars of "b" by j insertions); dp[i][0] = i (delete i characters of "ab" to get empty).
So dp[0][0]=0, dp[0][1]=1, dp[1][0]=1, dp[2][0]=2.
dp[1][1]: comparing "a" vs "b" — characters differ ('a' vs 'b'), so take 1 + min(dp[0][1], dp[1][0], dp[0][0]) = 1 + min(1,1,0) = 1.
dp[2][1]: comparing "ab" vs "b" — last characters match ('b' == 'b'), so dp[2][1] = dp[1][0] = 1 (no edit needed for this pair, inherit the diagonal).
Each cell reads only cells with a strictly smaller row, column, or both, which is why filling row by row, left to right, works. Final answer: dp[2][1] = 1 (delete the leading 'a').

## Complexity
Typically O(n · m) time and O(n · m) space, where n and m are the two dimensions (two string lengths, or a sequence length times a capacity). Space can often be reduced to O(min(n, m)) or O(m) by keeping only the current and previous row, since most recurrences only ever look one row back.

## Where it breaks
It breaks when a third independent quantity needs tracking (a second budget, a count of some other resource, or a "last action taken" flag) — at that point two indices no longer fully describe the state, and either a third dimension is needed or the state must be redesigned. It also breaks, performance-wise, when the two dimensions are both large (e.g., both up to 10^5), since O(n·m) becomes too slow — that's usually a sign a smarter structure (not more dimensions) is needed.

## Confusable with
| Also looks like | Tell them apart by |
|---|---|
| 17-1d-dp | If one of the two "dimensions" is actually fixed or derivable from the other (not truly independent), the problem often collapses to 1-D; genuine 2-D DP needs both indices to vary independently in the recurrence. |
| Grid BFS/DFS | Grid path *counting* or *cost-summing* problems are 2-D DP; grid problems asking for shortest path length in an unweighted maze, or connectivity, are graph traversal, not DP. |
| Backtracking with memoization | Recursion with two changing parameters, memoized, is 2-D DP by another name — recognizing the two-parameter recursion tree already has overlapping calls is what tells you a table will help. |

## Common traps
- Iterating in an order where a needed cell is not yet filled — easy to do by accident when the recurrence references both dp[i-1][j] and dp[i][j-1] but the loops are nested in the wrong order relative to what's needed first.
- Rolling the table down to 1-D too early, clobbering a value from the previous row that a later computation in the current row still needs — this optimization is only safe once the exact dependency pattern is fully understood.
