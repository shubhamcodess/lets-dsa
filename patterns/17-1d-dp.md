# 1-D Dynamic Programming

_Pattern id: 17-1d-dp · Depends on: 12-backtracking · Problems available: 45_

## The one-sentence idea
Break the problem into subproblems indexed by a single position, notice the same subproblems get solved over and over by brute force, and store each answer once so it's never recomputed.

## How to recognize it
- The question asks for a count of ways, a minimum cost, or a maximum value achieved over a sequence of choices.
- A brute-force recursive solution would be exponential, and tracing it reveals the same smaller subproblem being solved repeatedly under different call paths.
- The decision at position i depends only on a bounded window of earlier positions (i-1, i-2, or a small fixed set), not on the entire history in some unbounded way — so a single running index can summarize "how far you've gotten."

## The invariant
dp[i] is the answer to the problem restricted to just the first i elements (or the state ending at position i), and its value is computed using only strictly smaller indices — never something not yet determined.

## The shape
1. Define the state: decide precisely what dp[i] means in words — e.g., "the maximum sum of a subarray ending at index i," or "the minimum coins needed to make amount i." This sentence is the whole game; if it's fuzzy, everything after it will be wrong.
2. Write the recurrence: express dp[i] in terms of dp at smaller indices, matching exactly how the problem lets you extend a smaller solution into a bigger one (e.g., dp[i] = dp[i-1] + something, or a min/max over a few candidate predecessors).
3. Identify base cases: the smallest indices (i=0 or i=1) where the recurrence has nothing smaller to refer to, and must be set directly from the problem's definition.
4. Choose the iteration order: since dp[i] depends only on smaller indices, iterate i from small to large (or in whatever order guarantees dependencies are already filled) — this order matters because computing dp[i] before its dependencies exist gives a garbage or undefined value.
5. Read the final answer off the last computed state (often dp[n], or a max/min over all dp[i]) once the table is fully filled.

## The named algorithms
| Algorithm | What it computes | Key idea | Cost |
|---|---|---|---|
| Kadane's algorithm | The maximum-sum contiguous subarray | At each position, decide whether extending the previous best subarray is still worth it, or whether starting fresh from here beats carrying the previous sum forward | O(n) time, O(1) space |

Kadane's algorithm is the canonical 1-D DP: it keeps a single running value — the best subarray sum ending exactly at the current index — and at each step either extends it or resets it, because a negative running sum can never help a future subarray. The reason it works is the same reason all of 1-D DP works: the best answer ending at position i can be computed purely from the best answer ending at position i-1, with no need to re-examine earlier positions.

## Worked micro-example
Consider "minimum coins to make amount 5" with coins [1,2,5], where dp[i] means the minimum number of coins to make amount i.
Base case: dp[0] = 0 (zero coins make amount zero).
dp[1]: only coin 1 fits (coins 2 and 5 are too big). dp[1] = dp[1-1] + 1 = dp[0] + 1 = 1.
dp[2]: coin 1 gives dp[1]+1 = 2; coin 2 gives dp[0]+1 = 1. Take the minimum: dp[2] = 1.
dp[3]: coin 1 gives dp[2]+1 = 2; coin 2 gives dp[1]+1 = 2. dp[3] = 2 (both tie).
dp[4]: coin 1 gives dp[3]+1 = 3; coin 2 gives dp[2]+1 = 2. dp[4] = 2.
dp[5]: coin 1 gives dp[4]+1 = 3; coin 2 gives dp[3]+1 = 3; coin 5 gives dp[0]+1 = 1. dp[5] = 1.
Each dp[i] reads only dp values at strictly smaller amounts, which is why filling the table left to right (small amounts first) works. Final answer: dp[5] = 1.

## Complexity
Typically O(n · k) time, where n is the number of states (often the array length or a target value) and k is the number of transitions examined per state (often a small constant, or the number of choices like coin denominations). Space is O(n) for the full table, though many 1-D DPs can be compressed to O(1) or O(k) if dp[i] only ever depends on the last few entries.

## Where it breaks
It breaks when the "position" alone doesn't capture enough information to make the recurrence correct — for example, if the answer at position i also depends on some additional resource or budget that varies independently (how many items used, how much capacity remains). At that point the state needs a second dimension, which is 18-2d-dp. It also breaks if the recurrence needs to look arbitrarily far back rather than a bounded window, which usually means the state definition itself needs to change rather than just its indexing.

## Confusable with
| Also looks like | Tell them apart by |
|---|---|
| Backtracking / brute-force recursion | If the recursive solution has overlapping subproblems (the same (state) gets recomputed many times across different call paths), it's DP; if every recursive call explores genuinely distinct territory, it's plain backtracking with no memoization to add. |
| Greedy | If a single local choice at each step is provably always safe, greedy is simpler and correct; DP is needed precisely when you can't prove that, because a locally worse choice now might be required for a better outcome later. |
| 18-2d-dp | If the state needs two independent indices to describe (two strings, or a position plus a capacity), it's 2-D, not 1-D. |

## Common traps
- Choosing a state that does not capture enough information to make the recurrence correct — the classic failure is a dp[i] that answers a subtly different question than the one actually needed to build dp[i+1].
- Getting the base case off by one, or iterating in the wrong direction, so that dp[i] is computed before the values it depends on have been filled in.
